프로젝트에서 카카오﹒네이버﹒구글 로그인을 붙이게 되었다.

**소셜 로그인은 왜 페이지가 두 번이나 넘어갈까?**

우리 사이트 -> 카카오로 한 번, 
카카오 -> 우리 사이트로 한 번.

이 두 번의 리다이렉트에 OAuth의 설계 철학이 전부 들어있다.

## 등장인물 3명

OAuth를 처음 볼 때 헷갈리는 이유는 등장인물이 셋이기 때문이다.

- **사용자** - 카카오 계정을 가진 사람. 우리 서비스에 가입하려는 중이다.
- **우리 서비스** - 사용자가 누구인지 확인하고 싶지만, 비밀번호를 받고 싶지는 않다.
- **Provider(카카오﹒네이버﹒구글)** - 사용자의 신원을 이미 알고 있는 곳이다.

OAuth가 풀려는 문제는 이렇게 요약된다.
**"사용자의 비밀번호를 우리에게 알려주지 않으면서, Provider가 신원을 보증하게 하려면?"**

사용자가 우리 사이트에 카카오 비밀번호를 입력하는 순간, 이 목표는 무너진다.
그래서 비밀번호 입력은 반드시 카카오 화면에서 일어나야 하고 - **이것이 첫 번째 리다이렉트의 이유**
인증이 끝난 사용자를 우리 서비스로 되돌려보내야 하니 - **두 번째 리다이렉트도 필연적**

## 플로우 한 바퀴

```
[우리 서비스]                    [Provider(카카오)]

 ① "카카오 로그인" 클릭
 ② 카카오 인가 페이지로 이동 ────────▶ ③ 사용자가 카카오에 로그인·동의
    (client_id, redirect_uri,            (비밀번호는 여기서만 입력됨)
     scope, state를 실어서)
                                       ④ redirect_uri로 되돌려보냄
 ⑤ 콜백 도착 ◀──────────────────────     ?code=인가코드&state=...
 ⑥ 인가 코드를 토큰으로 교환
    (서버 간 통신, client_secret 사용)
 ⑦ 로그인 완료, 우리 서비스의 토큰 발급
```

각 단계에서 오가는 것들의 이름만 익혀도 절반은 끝난다.

- **client_id** - "우리 서비스가 누구인지" Provider에 알려주는 공개 식별자
- **scope** - 어떤 정보(닉네임, 이메일 등)까지 받을지의 범위
- **인가 코드(authorization code)** - ④에서 받는 짧은 일회용 티켓
- **client_secret** - ⑥ 교환 때 쓰는 우리 서비스의 비밀키. 절대 브라우저에 노출되면 안된다

## 왜 토큰이 아니라 "코드"를 줄까

④번이 이상하게 느껴질 수 있다. 
카카오가 어차피 신원을 확인했다면 그냥 토큰을 주면 될텐데, 왜 코드라는 중간 단계를 거칠까?

④번의 전달 수단을 보면 답이 나온다.
리다이렉트는 **브라우저 주소창**을 거친다.
주소창에 실린 값은 브라우저 방문 기록에 남고, 어깨 너머로 보일 수 있고, 서버 접근 로그에도 찍힌다.
여기에 토큰을 그대로 실으면 곳곳에 토큰이 흩뿌려지는 셈이다.

그래서 OAuth는 주소창에 **짧게 살고, 한 번만 쓸 수 있고, 그 자체로는 아무 권한도 없는** 인가 코드를 싣는다.
진짜 토큰은 ⑥번 - 주소창을 거치지 않는 서버 간 통신에서, client_secret을 아는 우리 서비스만이 교환할 수 있다.
코드가 유출되더라도 secret 없이는 무용지물이다.

> 과거에는 토큰을 주소창으로 바로 받는 Implicit Flow라는 방식도 있었지만, 노출 문제 때문에 현재는 사용하지 않도록 권고된다고 한다.

## redirect_uri와 state는 왜 있을까

②번 요청에 실리는 두 파라미터는 각각 공격 하나씩을 막고 있다.

**redirect_uri - 코드를 엉뚱한 곳에 배달하지 않기 위해**
만약 공격자가 인가 요청의 되돌아올 주소를 자기 서버로 바꿔치기할 수 있다면, 사용자가 로그인하는 순간 인가 코드가 공격자에게 배달된다.
그래서 Provider는 **개발자 콘솔에 미리 등록된 redirect_uri만** 허용한다.
소셜 로그인 개발 중 가장 자주 만나는 에러 (redirect_uri mismatch) 가 바로 이 검증에 걸린 것이다.

**state - 되돌아온 응답이 "내가 시작한 그 요청"인지 확인하기 위해**
로그인을 시작할 때 예측 불가능한 값을 만들어 실어 보내고, 콜백으로 돌아온 값과 대조한다.
이게 없으면 공격자가 **자기 계정의 인가 코드**를 담은 콜백 URL을 피해자에게 밟게 해서, 피해자를 공격자 계정에 몰래 로그인시키는 공격이 가능해진다.
이후 피해자가 그 계정에 저장하는 정보는 공격자의 것이 된다.
state는 "이 콜백은 이 브라우저가 시작한 로그인의 결과"임을 보증한다.

## 교환은 누가 - 콜백 위치의 두 가지 설계

⑤~⑥번을 누가 담당하느냐에 따라 아키텍처가 갈린다.

**방식 A: 콜백을 백엔드가 받기**
redirect_uri를 백엔드 주소로 등록한다.
코드 수신과 교환이 모두 서버에서 일어나고, 끝난 뒤 프론트로 한 번 더 리다이렉트하며 세션을 전달한다.
프론트가 할 일은 거의 없지만, "교환이 끝난 결과를 프론트에 어떻게 넘길 것인가"라는 설계 문제가 새로 생긴다.

**방식 B: 콜백을 프론트가 받기**
redirect_uri를 프론트 주소로 등록한다.
프론트의 콜백 페이지가 주소창에서 `code`와 `state`를 읽어 **우리 백엔드 API로 전달**하면, 백엔드가 client_secret으로 Provider와 교환하고 우리 서비스의 토큰을 응답한다.
프론트는 "코드 배달부", 백엔드는 "금고지기"로 역할이 나뉜다.

내 프로젝트는 방식 B였다.
콜백 라우트(`/login/oauth2/code/[provider]` 형태)를 프론트가 직접 구현하게 되므로, 성공·실패 분기를 프론트가 온전히 통제할 수 있다는 장점이 있다.
사용자가 카카오 화면에서 "취소"를 누르면 콜백에 `code` 대신 `?error=access_denied`가 실려 오는데, 이런 경우까지 다뤄야 완성이다.
취소는 에러가 아니라 정상적인 사용자 행동이기 때문이다.

> 백엔드 없이 100% 프론트에서 교환하는 구조도 있다. 브라우저는 client_secret을 가질 수 없으므로 PKCE라는 별도의 검증 장치를 쓴다. 모바일 앱이나 백엔드 없는 SPA에서 쓰는 방식이라, 여기서는 이름만 알아두고 넘어간다.

## 구현하며 밟은 함정: 일회용 코드 × React StrictMode

이론에서 "인가 코드는 일회용"이라고 배웠는데, 이 성질이 예상 못한 곳에서 발목을 잡았다.

React 개발 모드의 StrictMode는 effect를 **의도적으로 두 번 실행**한다.
콜백 페이지의 effect에서 코드 교환 API를 호출하면 - 같은 코드로 교환이 두 번 나가고, 두 번째는 반드시 실패한다.
첫 번째 교환이 성공했는데도 화면에는 에러가 뜨는, 개발 환경에서만 재현되는 유령 버그가 된다.

```tsx
// 콜백 컴포넌트 - 한 번 다룬 코드는 다시 교환하지 않는다
const handledCodes = new Set<string>();

useEffect(() => {
  if (!code || handledCodes.has(code)) return;
  handledCodes.add(code);

  exchangeCodeForToken(provider, { code, state })
    .then(saveTokensAndRedirect)
    .catch(showError);
}, [code, state]);
```

"일회용"이라는 이론적 성질 하나가, StrictMode라는 프레임워크 동작과 만나 실전 버그가 되는 경험이었다.
이론을 아는 것과 그 이론이 코드 어디에서 튀어나올지 아는 것은 다른 층위라는 걸 배웠다.

## 정리

- 리다이렉트가 두 번인 이유: 비밀번호는 Provider에서만 입력되어야 하고(1차), 인증된 사용자는 우리에게 돌아와야 한다(2차)
- 토큰 대신 코드를 쓰는 이유: 주소창은 노출되는 통로라, 거기엔 일회용 티켓만 싣는다
- redirect_uri 등록제는 코드 배달 사고를, state는 콜백 바꿔치기를 막는다
- 콜백을 프론트가 받는 구조에서는 성공뿐 아니라 취소·실패 분기까지 프론트의 책임이다
