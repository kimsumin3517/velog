2편에서 Access Token을 메모리에 두기로 했다.
메모리는 새로고침하면 사라진다.
그런데 사용자는 새로고침해도 로그인이 유지되기를 기대한다.
이 모순을 푸는 게 **세션 복구**다.

## 복구 절차

localStorage에 살아남은 Refresh Token이 열쇠다.
앱이 뜰 때:

```
localStorage에 refresh가 있나?
├ 없음 → 비로그인 확정 (API 호출 없이 즉시)
└ 있음 → 재발급 API 호출
    ├ 성공 → 새 토큰 쌍 저장 → 사용자 정보 조회 → 로그인 상태 복원
    └ 실패 → 비로그인 확정
```

"없음" 분기에서 API를 안 부르는 게 사소해 보여도 중요하다.
방문자 대부분은 로그인한 적 없는 사람들이고, 그들에게 헛된 네트워크 요청을 시킬 이유가 없다.

## 상태는 2개가 아니라 3개여야 한다

복구에는 시간이 걸린다 (재발급 왕복 수백 ms).
그동안 앱은 로그인 여부를 모른다.
이 "모르는 시간"을 비로그인으로 취급하면 - 로그인돼 있는 사용자에게 잠깐 로그아웃 화면이 번쩍이는 깜빡임이 생긴다.

그래서 상태가 3개다.

```ts
type AuthState =
  | { status: "loading";       user: null }   // 복구 진행 중
  | { status: "authenticated"; user: User }   // 로그인됨
  | { status: "guest";         user: null };  // 비로그인 확정
```

화면은 loading일 때 판단을 유보하면 된다.
"모른다"와 "아니다"를 구분하는 것 - 상태 설계의 기본인데 빼먹기 쉽다.

## Context가 아니라 모듈 스토어를 쓴 이유

React에서 전역 상태라면 Context부터 떠올리게 된다.
그런데 인증 상태에는 Context로 풀 수 없는 요구사항이 하나 있었다.

4편의 재발급 로직을 떠올려보자.
재발급이 최종 실패하면 로그아웃 상태로 전환해야 하는데, **그 전환을 일으키는 건 React 컴포넌트가 아니라 API 클라이언트(순수 모듈)다.**
Context 안의 상태는 React 바깥에서 바꿀 방법이 없다.

그래서 상태를 모듈에 두고, React는 구독만 하게 했다.

```ts
// 모듈 - React 바깥에서도 호출 가능
let state: AuthState = LOADING;
const listeners = new Set<() => void>();

export function setGuest() {          // API 계층이 직접 부를 수 있다
  state = GUEST;
  listeners.forEach((l) => l());
}

// React - 구독
export function useAuth(): AuthState {
  return useSyncExternalStore(subscribe, () => state, () => LOADING);
}
```

`useSyncExternalStore`는 이름 그대로 "외부 저장소를 React와 동기화"하는 훅이다.
**상태를 어디에 두느냐가 누가 그 상태를 바꿀 수 있느냐를 결정한다** - 이번 작업에서 얻은 가장 큰 교훈이다.

세 번째 인자(서버 스냅샷)를 항상 loading으로 둔 것도 이유가 있다.
SSR 환경에서는 서버 렌더와 클라이언트 첫 렌더가 같아야 하이드레이션이 깨지지 않는데, 복구는 브라우저에서만 일어나니 둘 다 loading으로 일치시키는 것이다.

## 실패에도 종류가 있다

복구 실패를 한 덩어리로 처리하면 안 된다.

- **재발급이 401** → refresh가 만료·무효로 확정. **토큰을 지운다.** 죽은 토큰을 남겨두면 매 부팅마다 헛된 재발급이 나간다.
- **네트워크 실패** → 토큰의 생사를 모른다. **지우지 않는다.** 지하철에서 앱을 열었다는 이유로 로그아웃시키면 안 되고, 다음 방문 때 다시 시도하면 된다.

3편에서 서버 에러와 네트워크 실패를 구분해둔 게 여기서 빛을 본다.

## 마지막 함정 - StrictMode, 또 너냐

복구 로직을 useEffect에서 실행하면, 1편에서 만난 그 친구가 또 온다.
React StrictMode는 개발 모드에서 effect를 두 번 실행한다.
가드 없이 두면 재발급이 두 번 나가고, rotation 때문에 두 번째가 첫 번째를 무효화한다.
간단한 실행 가드 하나로 막는다.

```ts
let started = false;

export async function restoreSession() {
  if (started) return;
  started = true;
  // ...복구 절차
}
```

## 시리즈를 마치며

다섯 편을 관통하는 흐름을 한 줄씩 되짚으면:

1. OAuth - 비밀번호를 받지 않고 신원을 확인하는 방법
2. 저장 - 백엔드 계약 위에서의 트레이드오프
3. 관문 - 화면이 인증을 모르게 하는 설계
4. 재발급 - 로직이 맞아도 동시에 돌면 틀린다
5. 복구 - "모른다"와 "아니다"를 구분하는 상태 설계

로그인 버튼 하나 뒤에 이만큼이 있다.
라이브러리를 쓰면 몰라도 되는 것들이지만, 알고 쓰는 것과 모르고 쓰는 것은 문제가 터졌을 때 갈린다.
