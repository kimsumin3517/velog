소셜 로그인에 성공하면 백엔드가 토큰 두 개를 응답한다.
Access Token과 Refresh Token.
이제 프론트엔드의 고민이 시작된다. **이걸 어디에 둘 것인가?**

검색해보면 "localStorage에 토큰을 저장하면 안 된다"는 글과 "다들 그렇게 쓴다"는 글이 공존한다.
이 글은 그 논쟁을 트레이드오프로 정리한 기록이다.

## 왜 토큰이 2개일까

먼저 JWT의 성질 하나.
JWT는 `헤더.페이로드.서명` 구조인데, 페이로드는 암호화가 아니라 인코딩이라 누구나 열어볼 수 있다.
대신 내용을 고치면 서명이 안 맞아 서버가 거부한다.
**"읽기는 공개, 위조는 불가"**가 JWT의 본질이다.

문제는 서버가 상태를 저장하지 않는(stateless) 구조라, 발급한 토큰을 중간에 무효화할 방법이 없다는 것.
도둑이 토큰을 훔치면 만료까지 자유롭게 쓴다.
그래서 수명을 짧게 잡아 피해 시간을 제한한다.

그런데 Access 하나만 짧게 쓰면 사용자가 30분마다 재로그인해야 한다.
그래서 역할을 나눈다.

| | Access Token | Refresh Token |
|---|---|---|
| 용도 | 모든 API 요청에 동봉 | 오직 재발급에만 사용 |
| 수명 | 짧음 (분 단위) | 긺 (일·주 단위) |
| 노출 빈도 | 매 요청 (높음) | 가끔 (낮음) |

자주 노출되는 놈은 짧게, 오래 사는 놈은 아껴 쓰기.
**위험 분산**이 핵심이다.

## 저장 선택지와 XSS

브라우저에서 값을 보관할 곳은 크게 넷이다.
localStorage, sessionStorage, JS 메모리(변수), 그리고 httpOnly 쿠키.

여기서 XSS 얘기가 나온다.
**XSS는 공격자가 우리 사이트 안에서 자기 스크립트를 실행시키는 공격**이다.
닉네임에 심은 스크립트가 화면에 그대로 렌더되면, 그 스크립트는 우리 사이트의 권한으로 돈다.
`localStorage.getItem("refreshToken")` 한 줄이면 토큰이 넘어간다.

httpOnly 쿠키는 JS가 아예 읽을 수 없어서 이 직접 탈취가 통하지 않는다.
그래서 "토큰은 httpOnly 쿠키가 정답"이라는 통설이 생겼다.

## 그런데 쿠키가 선택지에 없다면

여기가 많은 글이 건너뛰는 지점이다.
**쿠키는 서버가 심어주는 것이다.**
백엔드가 토큰을 응답 바디(JSON)로 주는 계약이라면, 프론트가 저장을 책임져야 하고 httpOnly 쿠키는 애초에 선택지가 아니다.
저장 위치 논쟁은 프론트 혼자 정하는 게 아니라 **백엔드 계약에서 출발**한다.

내 프로젝트가 정확히 이 경우였다.
남은 선택지 안에서 이렇게 절충했다.

- **Access → 메모리(모듈 변수)**
  매 요청에 실리는 위험한 놈이다. 변수에 두면 "정해진 키로 꺼내가는" 방식의 탈취가 통하지 않고, 어차피 수명도 짧다.
  새로고침하면 사라지지만, 그건 복구 로직이 해결한다. (이 시리즈 5편에서 다룬다)
- **Refresh → localStorage**
  새로고침 생존이 필수 요구사항이라 영구 저장소가 필요하다.
  XSS에 뚫리면 위험하다는 건 인정하고 들어가는 트레이드오프다.

이 조합이 성립하는 전제가 하나 있는데, 백엔드의 **Refresh Token Rotation**이다.
재발급할 때마다 refresh도 새로 발급되고 쓴 것은 즉시 무효가 된다.
훔친 토큰의 유효 기간이 사실상 "다음 재발급 전까지"로 줄어드는 셈이다.
실제로 Auth0의 SPA SDK도 localStorage 저장을 허용하는 조건으로 rotation을 요구하고, Supabase는 localStorage 저장이 기본값이다.
업계에서 통용되는 조합이라는 뜻이다.

## 1차 방어는 저장 위치가 아니다

솔직해질 부분.
XSS가 뚫리면 어디에 저장했든 결국 다 뚫린다.
메모리에 있어도 실행 중인 스크립트는 API 호출을 가로챌 수 있다.
저장 위치는 2차 완화책이고, **1차 방어는 XSS 자체를 막는 것**이다.
React가 모든 값을 기본 이스케이프해주는 게 그 방어선이고, `dangerouslySetInnerHTML`을 안 쓰는 습관이 저장 위치 고민보다 먼저다.

> 더 안전한 상위 구조도 있다. 프론트 서버가 API 프록시가 되어 토큰을 httpOnly 쿠키로만 다루고 브라우저 JS에는 토큰이 아예 존재하지 않게 하는 BFF(Backend For Frontend) 패턴이다. 서버 계층이 하나 추가되는 큰 결정이라, 규모가 커지면 검토할 카드로 남겨뒀다.

## 정리

- 토큰이 2개인 이유: 노출 잦은 것은 짧게, 오래 사는 것은 아껴 쓰는 위험 분산
- 저장 위치 논쟁의 출발점은 프론트 취향이 아니라 백엔드 계약이다
- 바디로 받는 계약이라면: access는 메모리, refresh는 localStorage + rotation 전제가 통용되는 절충
- 어디에 저장하든 1차 방어는 XSS 예방이다
