Access Token의 수명은 짧다.
30분마다 사용자에게 재로그인을 시킬 수는 없으니, **만료 시 사용자 몰래 재발급받고 원래 요청을 재시도**하는 로직이 필요하다.
말로는 간단한데, 여기서 이 시리즈 전체에서 가장 어려운 문제를 만났다.

## Rotation - 재발급의 규칙

내가 연동한 백엔드의 재발급 API는 rotation 방식이었다.
재발급하면 access만 주는 게 아니라 **refresh도 새로 주고, 방금 쓴 refresh는 즉시 무효화**한다.

왜 이렇게 할까.
refresh가 탈취됐다고 생각해보자.
rotation이 있으면 토큰은 **일회용**이라, 도둑과 주인 중 먼저 쓴 쪽만 성공한다.
두 번째 시도는 401이 나고, 서버는 "무효화된 토큰의 재사용"을 보고 탈취를 감지할 수 있다.

보안은 좋아지는데, 프론트에는 의무가 생긴다.
**응답의 새 refresh로 반드시 교체할 것.**
나는 이 의무를 사람의 기억력이 아니라 타입에 맡겼다.
저장 함수가 쌍만 받게 만들면, access만 갱신하는 코드는 컴파일이 안 된다.

```ts
export function setTokens(pair: { accessToken: string; refreshToken: string }) { ... }
// 한쪽만 갱신하는 API는 의도적으로 만들지 않았다
```

## Race Condition - 로직이 다 맞아도 틀리는 순간

화면이 마운트되면서 API 3개를 동시에 쏘는 건 일상이다.
access가 만료된 상태라면 이런 일이 벌어진다.

```
요청 A ── 401 ── 재발급 시작 (refresh_1 사용)
요청 B ── 401 ── 재발급 시작 (refresh_1 사용)  ← A와 동시에!
요청 C ── 401 ── 재발급 시작 (refresh_1 사용)

A의 재발급 성공 → rotation으로 refresh_1 즉시 무효
B의 재발급 도착 → refresh_1은 이미 무효 → 401 "다시 로그인해 주세요"
→ 내 코드: "재발급 실패네, 로그아웃!" → 사용자 튕김
```

요청 하나하나의 로직은 전부 옳다.
**동시에 돌았을 뿐인데 서로를 죽인다.**
이게 race condition이고, "가끔 이유 없이 로그아웃돼요"라는 재현 안 되는 버그의 전형적인 원인이다.

## Single-flight - 해법은 15줄

"재발급은 동시에 하나만. 이미 진행 중이면 새로 시작하지 말고 **그 결과를 같이 기다려라**."

```ts
let inFlight: Promise<RefreshResult> | null = null;

export function refreshTokens(): Promise<RefreshResult> {
  inFlight ??= doRefresh().finally(() => {
    inFlight = null;
  });
  return inFlight;   // A·B·C 모두 같은 promise를 기다린다
}
```

진행 중인 재발급 promise를 모듈 변수에 저장해두고, 있으면 그걸 반환한다.
A가 시작한 재발급을 B·C가 함께 기다렸다가, 끝나면 셋 다 새 토큰으로 재시도한다.

여기에 안전핀 두 개를 더해야 완성이다.

- **재시도는 딱 1회.** 재발급 후에도 401이면 그건 다른 문제다. 무한 루프 차단.
- **재발급 요청 자체는 관문의 401 처리를 타면 안 된다.** 안 그러면 재발급이 재발급을 부른다. 나는 이 요청만 관문을 거치지 않는 별도 모듈로 분리했다.

그리고 트리거 조건을 좁히는 것도 중요하다.
백엔드가 401을 코드로 세분화해준다면(만료 / 위조 / 토큰 없음), **재발급이 의미 있는 건 "만료" 하나뿐**이다.
위조된 토큰에 재발급을 시도하는 건 무의미한 왕복이다.

## 남은 문제 - 멀티탭

single-flight는 한 탭 안의 경합만 막는다.
탭이 두 개면? 각 탭은 서로의 promise를 모르니, 거의 동시에 재발급하면 rotation 충돌이 또 일어날 수 있다.

완전한 해결(Web Locks, BroadcastChannel)은 다음 기회로 미루고, 완화책 두 개만 넣었다.

- refresh를 메모리에 캐시하지 않고 **재발급 직전에 항상 localStorage에서 읽는다** - 다른 탭이 교체한 최신 값을 자연히 쓰게 된다
- 재발급이 401을 받아도 바로 사망 선고하지 않고, **저장소 값이 그새 바뀌었는지 한 번 확인**한다 - 바뀌었다면 다른 탭이 방금 재발급한 것이니 그 값으로 한 번 더 시도한다

## 정리

- rotation은 탈취 감지를 위한 설계이고, 프론트는 "쌍 교체"의 의무를 진다
- 로직이 다 맞아도 동시에 돌면 틀릴 수 있다 - 재발급은 single-flight로
- 안전핀: 재시도 1회, 재발급 요청은 관문 제외, 트리거는 "만료" 코드로 한정
- 멀티탭은 남은 숙제 - 저장소 재확인으로 완화만
